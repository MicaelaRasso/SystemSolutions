## Working agreement

- Implement one phase at a time, with dependency-ordered subgroups. At the end of each phase, review the changes, report what was implemented and verified, list gaps and issue status, and wait for the user's explicit confirmation before starting the next phase.
- Every spawned subagent must use `gpt-6-luna` with low, medium, or high reasoning effort; use high when the task requires analyzing repository or domain context. Agents share the worktree, so assign non-overlapping files or coordinate edits.
- Implementation scope is **database, Edge Functions, and APIs**; do not build new frontend pages or features. If a relevant frontend already exists, connect it to the new APIs and verify that integration. Otherwise, leave the API ready for a future frontend. Existing Phase 1 frontend edits are disclosed in [phase-1-page-inventory.md](phase-1-page-inventory.md). A ticket with UI acceptance criteria cannot be called fully complete merely because its API exists.
- Do not infer permission to deploy to production, alter production secrets, or close/relabel issues. Recheck the current issue state and ask for approval when those actions become relevant.
- Preserve unrelated worktree changes. Before editing, inspect `git status`, distinguish pre-existing changes from phase work, and read the current issue bodies/comments. Follow `AGENTS.md`, [issue-tracker.md](agents/issue-tracker.md), [domain.md](agents/domain.md), `CONTEXT.md`, the relevant ADRs, and the applicable skills. For Next.js code, read the relevant installed `node_modules/next/dist/docs/` guide first.

## Phase 1 implementation and unresolved review

The current worktree includes account lifecycle/current-state enforcement, auditable visit transitions, certificate validation/offline handling, visit administration, and a versioned replacement-parts catalog. Some #53–59 implementation predated this phase in commit `cbe98e2`; the phase reconciled and extended it. Relevant artifacts include:

- [ADR-0012](adr/0012-versioned-replacement-parts-and-capture-boundary.md), `CONTEXT.md`, and `integration.md` for the domain and API decision.
- `supabase/migrations/20261005154045_cuenta_lifecycle_current_state.sql`, `20261005154315_preserve_visit_audit_device_time.sql`, `20261005154526_certificate_capture_offline_validation.sql`, `20261005160000_visit_administration_lifecycle.sql`, and `20261006122725_visit_replacement_catalog_snapshots.sql`, with corresponding `supabase/tests/database/*.test.sql` tests. A separate pre-existing, untracked `20261003203856_fix_valve_composite_assignment.sql` must not be mistaken for Phase 1 work.
- `supabase/functions/identity-admin`, `service-workflow`, and `offline-sync`, plus shared route/transport logic; API client contracts in `src/lib/api/`. See [phase-1-page-inventory.md](phase-1-page-inventory.md) for the frontend changes already present and their purpose. No new page route was added.

Catalog rule confirmed by the user: Administrators may edit Repuestos options until a visit begins. A Taller Móvil may have downloaded an older catalog while online; when it starts a visit offline, **that downloaded version** is frozen for the visit, not whatever is live at eventual synchronization. Later admin edits affect only future snapshots. Backend endpoints/contracts now expose catalog revisions and selected part IDs/labels, record a device's working-set download, pin the downloaded revision at visit start, and validate later certificate drafts against the pinned snapshot. Legacy records remain readable. Check the latest ADR and `integration.md` for exact request/response shapes.

API continuation anchors: admin Repuestos create/update/delete/reorder publishes immutable UUID revisions with ordered `{id,label}` options; `GET /certificate-capture/catalogs` exposes `replacement_catalog_version` and `replacement_parts`; `POST /offline/working-set` with `{device_id}` returns visit-specific `certificate_catalogs` and records the device download (legacy GET remains); `POST /visits/:id/start` with `{device_id,replacement_catalog_version_id}` checks that download and pins the version (legacy empty body pins the live version); offline `start_visit` through `POST /visits/:id/sync` preserves the pin. New certificate drafts carry `repuestos.catalog_version` and are validated against that visit's snapshot. Check source/tests for exact wrappers and error codes before extending these APIs.

Verification already reported for the code state before this handoff: `npm test` (25 files / 231 tests), lint, typecheck, build, focused Edge route tests (3 files / 71 tests), and `git diff --check` passed. **SQL migrations and database tests have not run**: local `supabase status` cannot connect to Docker (`/var/run/docker.sock` unavailable). The user accepted Phase 1 with this verification gap; acceptance does not mean database verification or production readiness.

Outstanding follow-up before treating the implementation as database-verified: restore access to an appropriate local Supabase/Docker environment (or obtain an approved equivalent), apply/test migrations, run database tests and lint, inspect RLS/security behavior and migration ordering, and address findings.
