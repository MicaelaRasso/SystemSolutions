Follow `AGENTS.md`, [issue-tracker.md](agents/issue-tracker.md), [domain.md](agents/domain.md), `CONTEXT.md`, the relevant ADRs, and the applicable skills. ### Phase 4 Revision 2 — Resend transactional email

The agreed revision now has a local implementation. Resend is the shared SMTP provider for Supabase Auth and application notices, with the sender name `System Solutions`. Auth emails cover invitations/resends, password recovery, email-change verification, and the related security notice. Local Auth templates use Spanish copy, the System Solutions wordmark and navy/cyan palette, responsive layouts, and visible fallback URLs. Supabase's local Auth template config supports HTML content paths; application Edge emails include both plain-text and HTML MIME alternatives. Auth link tracking must be disabled. Application Edge Functions use Resend SMTP on port 2587.

Application notices include one certificate-expiry email per finalized certificate, targeted 30 calendar days before expiry when the Cliente's `aviso_vencimiento` flag is enabled, and one grouped pending-signature email when a visit closes without the Cliente's signature. Expiry processing runs daily at 09:00 in `America/Argentina/Buenos_Aires` and catches up missed notices while the certificate remains unexpired. Signature email goes to the Cliente's single MVP account, summarizes the Yacimiento and affected Plantas/locaciones, links to the existing certificate page, and is not repeated.

The revision exposes `GET /email-deliveries`, `GET /email-deliveries/:id`, and `POST /email-deliveries/:id/retry` to Súper Administrators only. Delivery records prevent duplicate notice creation; temporary SMTP failures can retry, uncertain outcomes require explicit review, and each manual retry requires a reason and audit record. A visit close wakes the worker immediately on a best-effort basis; the scheduled worker is the durable fallback. APIs report only queue and SMTP transaction outcomes known to the application; they do not claim recipient-server delivery, bounce, open, or click status. Auth delivery status is not mixed into the application's retry API and uses the existing Auth-specific resend/recovery flows. No frontend is added. Production domain verification, SMTP credentials, Auth dashboard settings, and worker schedules remain deferred to owner setup and are documented in [the Resend setup runbook](runbooks/resend-email-integration.md); no production configuration is authorized by this revision. Migration and Edge Function runtime verification were not run in this implementation session; follow the repository's documented Docker limitation before accepting database behavior.
